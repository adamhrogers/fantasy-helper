# ADR 0030: Push: the report jobs tell the phone, once, after a report is saved

**Status:** Accepted · 2026-11-22 · builds on ADR 0026 (reports saved in the cloud), 0027 (secrets per process), 0028 (the morning is a chain) and 0029 (the API)

## Decision
- **The report jobs send the push, not the API.** `daily` and `weekly` call `pipeline/notify.py` after their reports are committed. The API only hands the app the *public* key (`GET /v1/push/public-key`) and stores a device's subscription; it can't notify anyone.
- **The private key is readable by `fh-reports` only.** `fh-vapid-private-key` is mounted on the `daily` and `weekly` jobs and nowhere else: not the snapshot jobs, not the migration job, not the API (which gets `fh-vapid-public-key`). Workflow tests pin who gets which secret, the same way they pin the encryption key.
- **After commit, once.** A push announces a report that is saved, never one that could still roll back, so it is sent after the run's transaction is committed and never on `--dry-run`. Migration 0008 adds `reports.notified_at`. One push goes out per user, kind and date: if any of those reports is already marked, the run stays quiet; after at least one device accepts the push, all of them are marked. A rerun that *replaces* a report (a code fix, a late projection) keeps the mark, because the replacement carries it over. A league that fails in the morning and is built by the rerun doesn't start a second push for the day. The notification's tag is `daily-2026-11-20` (or `weekly-…`), so even a race between two runs shows once on the phone.
- **The network call is never inside a database transaction.** The notifier reads what it needs in one short transaction, sends, then writes what happened (devices stamped or deleted, reports marked) in another.
- **Push never fails a run.** The report is built either way, and the chain continues. What the push services say is read in four ways:
  - **Accepted** (HTTP 200 to 202): the device is stamped (`last_success_at`) and the report marked.
  - **Gone** (404, 410): the subscription is dead (the app was removed, the permission withdrawn); the row is deleted. This never warns.
  - **Refused** (400, 401, 403, 413): our credentials are wrong (the VAPID key or the app's address). The run ends with a warning, the device is kept (it isn't lost), and the report is left unmarked so a rerun after the fix announces it.
  - **Failed** (429, 5xx, no answer in time, or a redirect): the same, minus the blame: a warning, the device kept, a rerun tries again.
  A warning is a run event on the ops topic ([run-events.md](../runbooks/run-events.md)), with the push service's host, the status and the reason, and never an endpoint, a key or card text. A user with no devices, or a laptop with no push settings, is quiet and marks nothing.
- **The weekly overview notifies on Mondays only; the daily report every morning.** The weekly overview is rebuilt every morning (ADR 0026), and two notifications a minute apart every day would be noise. The weekday is one constant, `WEEKLY_NOTIFY_WEEKDAY` in `pipeline/notify.py` (0 is Monday), and it is Adam's to change. "Monday" is Monday in the user's own time zone, not UTC.
- **Every push shows a notification.** On iOS, Safari takes the permission away from a web app that receives a push and shows nothing. The service worker's `push` handler has no early return: a message that can't be read becomes a plain "Fantasy Helper" notification. A test fails if a path to `showNotification` can be skipped.
- **A message carries counts and a path, never text from a report.** It passes through Apple's, Google's or Mozilla's push service on its way to the phone, so it holds a title, a line like "9 cards in 2 leagues.", one of two paths (`/today`, `/week`) and the tag. It is built from what is saved, so it can't say more than the report does. Under 4 KB (Apple's limit; a check raises before anything bigger is sent), TTL 6 hours (a notification about a morning report isn't worth showing after lunch). The service worker opens only those two paths, whatever a message says.
- **A device's address must be on a known push service** (added 2026-11-23, after the review of this PR). The address comes from the browser, through a signed-in user, and the report jobs send a request to it, so any address would let whoever holds a sign-in point the morning job at any server, or hold it open. The list is one place, `domain/push.py` (`PUSH_SERVICE_HOSTS`, `PUSH_SERVICE_SUFFIXES`), read by both sides: exact hosts `web.push.apple.com` (Safari), `fcm.googleapis.com` (Chrome and the other Chromium browsers) and `updates.push.services.mozilla.com` (Firefox), and the exact suffix `.notify.windows.com` (Edge; Microsoft's hosts are regional). The address must also be `https`, plain ASCII, with no whitespace, backslash, user name, password or port, so every URL parser reads the same host. **The API refuses anything else with a 422, before saving.** **The sender checks again before sending,** so a row saved before the list existed, or written another way, is never sent to: it comes back `blocked`, is deleted (the API would never save it again), and the run warns once, naming its host, in case the list is missing a real browser's service. **Redirects are never followed.** **Time is capped by the clock:** the HTTP timeout is 5 seconds per request, but it applies to each read, so a server that trickles its answer could outlast it; each send also gets at most 8 seconds by the clock (`SEND_LIMIT_SECONDS`, on a daemon thread that is abandoned, not waited for) and the whole push 30 (`PUSH_LIMIT_SECONDS`), in `pipeline/notify.py`. A device past either limit is a failed send: a warning, and a rerun tries again. Push still never fails a run.
- **The VAPID subject is the app's own address, taken from `fh-app-origins`.** Apple refuses a subject that isn't a URL or a `mailto:`. The first address in `fh-app-origins` (the same secret the API's CORS list comes from) is the app, and it is mounted on the report jobs as `FH_APP_ORIGINS`. It must be `https` and not the `.invalid` placeholder, or the job says so by name. The app's address is in no file in this repository (the secret holds it), and no email address is used.
- **The keys are made, not typed.** `scripts/vapid-setup.sh` makes the pair inside one Python process, and that process hands each half to `gcloud secrets versions add --data-file=-`. The private key is never printed, never in a command line, never in a shell variable and never on disk; only the public key is printed (every browser is handed it anyway). The pair is checked before it is saved: the push library must read the private key the way the jobs will, and the public key must be the 65-byte uncompressed point a browser subscribes with. `gcp-secrets.sh` refuses the two names ("is made, not typed") so a typed value can't stand in for them.
- **The script refuses to run twice,** and `--rotate` makes you type the word. A device's subscription is tied to the public key it was made with, so a new pair orphans every subscription: pushes to them are refused or lost until each device turns notifications off and on again. The app notices (the subscription's key differs from the server's) and shows "off" with the button to turn it on, which replaces the old subscription.
- **`fh push test` checks the whole path from the cloud.** It runs as the `daily` job with its command replaced (`gcloud run jobs execute daily --region us-east4 --args=push,test --wait`), so it has the private key, the address and the database with nothing new to set up. It sends one test notification to every device and prints, per device, which push service answered, the status and what it means; the same lines go to the ops topic, because `--wait` only says passed or failed. It exits 0 only if every device was notified. It isn't a morning run: no watchdog ping, no hand-over to `weekly` (the job has `FH_NEXT_JOB` set), and a test checks that its source doesn't mention either.
- **The library is `pywebpush`.** Its traps are pinned by tests that run the real library against a fake push service which decrypts the message and checks the VAPID token: it changes the claims dictionary it is given (a fresh one per send), it has no timeout unless one is passed (5 seconds), it follows redirects unless its session refuses them (ours does), its errors come as its own exception or a bare `requests` one (both are read), and the private key must be the raw 32-byte value in URL-safe base64, which is what `vapid-setup.sh` stores.

## Why
The job is the thing that knows a report is ready, and it already holds the database and the secrets of the morning. The internet-facing service shouldn't hold the key that can notify every user (ADR 0029 keeps it away from the encryption key for the same reason). Sending after the commit means a push is never about a report that vanished; marking it once means a rerun, which is routine, never buzzes the phone twice. A push that can't be delivered must not cost the report, because the report is the product and the push is a convenience, so every failure is a warning rather than a failed run, and every warning says which side is wrong. Counts and a path keep anything private out of a third party's service. Reusing `fh-app-origins` for the subject avoids a second secret that could drift from the first.

## Rejected
- **The API sends the push.** It would need the private key, and it doesn't know when a report is ready.
- **Sending inside the run's transaction.** It would announce a report that could still roll back, and hold a database transaction open across the network.
- **Marking the report before sending.** A crash between the two would lose the push for the day.
- **One push per league.** Several phones buzzes for what is one morning.
- **The weekly overview every day.** Noise. A Monday-only default, with a constant, is enough.
- **A separate secret for the VAPID subject.** It could drift from the app's real address, and Apple refuses a subject that isn't one. It would also be one more secret to fill by hand.
- **A `mailto:` subject.** It would need an email address in a secret or, worse, in the repository.
- **Any https address for a device** (the first version of this PR). The jobs would send to wherever a signed-in user pointed them. **A loose match on the host** (a substring, or a suffix without the leading dot) would let `web.push.apple.com.attacker.example` or `evilnotify.windows.com` through; the list is exact hosts and dot-anchored suffixes.
- **Only an HTTP timeout.** It is per read, so it can't bound a send against a server that answers slowly on purpose; the clock's limits can.
- **Writing the protocol ourselves** (`http-ece` and `py-vapid` directly). `pywebpush` is a thin wrapper over those two and is maintained; owning the encryption and token code is a worse risk than its extra dependencies, which include `aiohttp` (it comes with the library's async path, which isn't used here).
- **Typing the private key into `gcp-secrets.sh`.** A key that is made, not typed, can't be mistyped or leave a copy in a password manager's clipboard history.
- **Silent pushes, or a notification only when something changed.** iOS revokes the permission for an app that shows none.

## Consequences
- **Rollout order matters** ([phone-app.md](../runbooks/phone-app.md) Part 3): `scripts/gcp-setup.sh infra` (creates the two empty secrets and says who may read each), then `scripts/vapid-setup.sh`, then the merge (the deploy mounts the secrets; a mounted secret with no enabled version fails the deploy), then turning notifications on in the app, then `fh push test`, then waiting for a real 06:17.
- **The first real push may surface surprises.** Apple's answers are the part the tests can't reproduce. That is why every refusal names the push service, the HTTP status and the reason, why `fh push test` exists, and why the runbook has a "no notification came" table.
- **Moving the app to another address** (a domain, at the beta) changes the VAPID subject (it follows the first address in `fh-app-origins`) and means reinstalling the app on the phone anyway (ADR 0009), so it is a new subscription.
- **Notifications are per device and per browser.** A laptop that turns them on has its own subscription row; `fh push test` and the morning push reach every one.
- **If push later needs another kind** (a lock reminder before tip-off, an alert), it is another `PushMessage` through the same sender and the same two paths. Product push is the phone app's; ops notifications stay on the ntfy topic (ADR 0011).
- Installing the dependency adds `pywebpush` and its dependencies to the lockfile, which Dependabot keeps current (ADR 0024).
