# ADR 0028: The morning is a chain: snapshot, then daily, then weekly

**Status:** Accepted · 2026-11-15 · replaces the three separate morning clocks of ADR 0025 and 0026

## Decision
- **Only the morning snapshot is on a clock** (Cloud Scheduler, 06:17 Eastern). **`daily` and `weekly` have no schedule.** The snapshot starts `daily`, and `daily` starts `weekly` when it finishes. Nothing downstream starts until what it depends on is done, however long that takes.
- **"Ready" means every dataset of the morning set saved and passed its checks.** The snapshot counts a dataset that failed, or that was saved but looked wrong (a half-empty projections file), as failed, so one bad dataset is an incomplete snapshot. Only a complete one writes a **completion marker** (`fh/snapshot_complete`, a tiny object in the raw store) and starts `daily`. A dataset reused from an earlier run that day (Sleeper's player list is fetched once a day) is read back from its saved sidecar, and a flagged one counts as incomplete too.
- **If the snapshot is incomplete, nothing downstream runs.** The snapshot's own alert says what failed (counts and kinds only), a quiet "Daily report not started" note says what didn't happen, and Healthchecks' `daily` check alerts at 07:45 that the report isn't coming. Re-running the snapshot (`gcloud run jobs execute snapshot-morning`) re-fetches what failed, and if everything now passes it marks the morning complete and restarts the chain.
- **The daily and weekly runs still check for the marker before they begin** (`--require-snapshot-today`, which now means "a complete morning snapshot from today"). With the chain it passes at once; it exists for runs started any other way (by hand, a retry), which wait for it, then fail with "no complete morning snapshot yet". A run started by hand on the laptop doesn't insist.
- **`weekly` starts after `daily` finishes, whatever its result**, unless `daily` never got going (the check failed or it crashed). The overview is its own product and checks its own inputs: one league failing in the daily run shouldn't cost the day's overview. Both are still held to the same completion marker.
- **Each job can start only the next one.** The hand-over is a call to the Cloud Run API, made with the job's own service account (`adapters/cloud_run.py`, token from the metadata server: no key file). `scripts/gcp-setup.sh` grants `run.invoker` on `daily` to the snapshot's account and on `weekly` to the report account, and nothing broader: a compromised job can start the next link, never change what it runs. The deploy sets each job's `FH_NEXT_JOB`; the laptop has none, so a hand run never starts a cloud job.
- **If the hand-over fails** (the API refused, Google was down for three tries), the data is saved and marked, and the phone gets an urgent "couldn't start daily" alert. The job exits 3 and its check goes down.
- **A run fails only when a part failed.** `daily` and `weekly` exit non-zero (and ping `fail`) only when a league failed or the run couldn't finish. Warnings (a Sleeper player not linked yet, a matchup that spans two weeks, a database nearing its quota) go to the phone as a warning and are recorded as DEGRADED, but the run exits 0. Conditions that last for weeks would otherwise raise a "down" alert every morning and bury the failures that matter.
- **Healthchecks schedules for chained jobs start at the chain's start.** A cron check expects a ping after each of its times, so a job that finishes at 06:19 must not have a 06:45 cron time (it would expect another ping at 06:45). `daily` and `weekly` use `17 6 * * *`, the snapshot's time, and a grace that ends at the alert deadline: 07:45 for `daily`, 08:00 for `weekly`. `scripts/jobs.conf` holds all of it, with who starts whom, and a test checks the deadlines.
- **Setup errors alert at once.** `daily` and `weekly` read their settings and open the raw store inside the watchdog, so a bad secret pings `start` and `fail` immediately instead of waiting out the grace.

## Why
Adam asked (2026-11-15, reviewing PR #16): the morning shouldn't be three jobs that happen to be scheduled near each other. Everything has to be in before the daily report runs, and if anything fails it shouldn't run. The review had found the gap: the first design's freshness check looked only at box scores, so a snapshot that saved those but failed on projections would still have started a daily run from yesterday's projections. A call in the registry can never be edited (ADR 0005), so "mostly fresh" isn't good enough to log one.

A chain turns timing into dependency. A clock can only guess how long the snapshot takes; a hand-over knows. It also removes the wait-and-retry window that the first design needed, and with it the question of what 06:45 means on a slow morning.

## Rejected
- **One `morning` job that runs all three steps in one container:** truly sequential and simple to reason about, but the snapshot would need the database account. A bad database secret then stops the job from starting at all, and a missed snapshot can't be recovered (ADR 0014). The snapshot must not depend on the database being reachable.
- **Cloud Workflows:** the right tool for orchestration, but a new service, a new account and a new language, and its steps can't be exercised locally. The chain here is a dozen lines of Python with tests.
- **Gating on "today's file exists":** a flagged payload is saved as evidence, so it exists and looks fresh. The marker is written only when everything passed.
- **Three Cloud Scheduler entries with a gate:** the design this replaces. It works, but it's three guesses about timing, and a late snapshot means a daily run that waits and may give up.
- **Running the daily report on partial data when something optional failed:** Adam's call is no. Every dataset is "everything", and a failed one means no report that day, with a clear reason.
- **Starting `weekly` only if `daily` fully succeeded:** it would skip the overview for a flaky league, and the weekly run already guards its own inputs.

## Consequences
- **The chain has four places to break, and each says so:** an incomplete snapshot (the snapshot's alert, then `daily`'s late check at 07:45), a marker that can't be written (urgent alert, no daily), a hand-over that fails (urgent alert, no next job), and a run that fails (its own alert). The runbook says how to restart from each ([prod-database.md](../runbooks/prod-database.md)).
- **A degraded snapshot now stops the morning.** Before, a failed optional dataset still let a daily run go. That's the requested behavior; it means one flaky source on a given morning costs that day's report.
- **One small object a day** (`fh/snapshot_complete/…`) appears in R2. Ingest ignores it, and `fh raw upload` copies the laptop's along with the data it vouches for.
- **The laptop's and GitHub's snapshot copies write a marker but never start anything.** Their `FH_NEXT_JOB` is unset.
- **The deploy path needs a person for some Dependabot updates.** The deploy's identity can deploy code that reads the prod database and the key that decrypts every league login, and every action in the job can ask GitHub for the token that identity uses. So the auto-merge job leaves a Dependabot PR open when it changes `deploy.yml`, the `Dockerfile` or `.dockerignore`: every Docker update and, because `actions/checkout` is in the deploy job, every grouped Actions update. Python updates still merge themselves (ADR 0024).
- **A new link in the chain** means a line in `jobs.conf` with `after JOB`, a `deploy` line with its next job, and a run of `scripts/gcp-setup.sh infra` and `scripts/healthchecks-setup.sh`. `tests/unit/test_workflows.py` fails if the three disagree.
